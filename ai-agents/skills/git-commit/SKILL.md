# Git Commit

確定した変更を、安全でレビューしやすいGitコミットとして記録する。

このSkillは新しいコミットの作成だけを対象とする。

既存コミットのrebase、squash、fixup、分割、メッセージ変更などの履歴編集は行わない。履歴編集が必要な場合は、ユーザーから明示的な依頼を受けたうえで、専用の手順またはSkillを使用する。

## コミット可能か確認する

次の条件をすべて満たしてからコミットする。

- 依頼された変更が実装されている。
- 今回の依頼範囲に未完了箇所が残っていない。
- 今回の変更によって発生した既知の不具合が残っていない。
- 必要なフォーマット、静的解析、テストが完了している。
- コミット対象の差分を既存のユーザー変更から分離できる。
- コミット対象がレビュー可能な単位に整理されている。

作業対象外の既存問題を発見した場合は、今回のコミットを妨げる問題か判断する。

今回の変更と無関係であり、コミットの正当性に影響しない既存問題は、必要に応じてユーザーへ報告するが、それだけを理由にコミットを中止しない。

ユーザーからコミットしないよう明示された場合は、その指示を優先する。

コミットできない場合は、次をユーザーへ報告する。

- コミットできない理由
- 実行した確認や検証
- 未コミットの変更内容
- 必要な次の対応

## 検証方法を決定する

フォーマット、静的解析、テストなどの検証コマンドは、次の優先順位で決定する。

1. ユーザーが指定したコマンド
2. `AGENTS.md` などのリポジトリ規約に記載されたコマンド
3. `mise.toml`、`Makefile`、`justfile`、`package.json`、CI設定などに定義された標準タスク
4. 変更対象に対して合理的に実行可能な個別コマンド

変更に関係しない検証を無制限に実行しない。

検証を実行できない場合は、実行できなかった理由を報告する。

## 作業ツリーを確認する

コミット前に次を実行する。

```bash
git status --short
git diff
git diff --cached
```

必要に応じて、次も確認する。

```bash
git status
git diff --stat
git diff --name-only
git diff --cached --stat
git diff --cached --name-only
```

以下を確認する。

- 変更ファイルが今回の依頼範囲と一致している。
- 既存のユーザー変更を含んでいない。
- 不要な生成物、キャッシュ、ログ、大容量ファイルが含まれていない。
- 秘密情報や個人環境固有の情報が含まれていない。
- 内容変更と無関係なフォーマット変更が混ざっていない。
- 意図しないファイル削除やファイル移動がない。
- ステージ済み変更と未ステージ変更の違いが把握できている。

未追跡ファイルが存在する場合は、ファイル名だけで判断せず、コミット候補の内容を確認する。

特に次のようなファイルや値をコミットしない。

- `.env` などの環境変数ファイル
- 秘密鍵、証明書の秘密情報
- APIキー、アクセストークン、パスワード
- クラウドやサービスの認証情報
- 個人環境固有の設定
- ログ、キャッシュ、一時ファイル
- 意図せず生成されたバイナリや大容量ファイル

秘密情報が含まれている可能性がある場合は、コミットせずユーザーへ報告する。

## コミット単位を決定する

コミット単位はファイル数ではなく、変更理由で判断する。

1つのコミットは、1つの目的、理由、または独立して説明できる変更を表すものとする。

次の変更は、同じ目的を成立させる場合は同一コミットに含めてよい。

- 実装と、その実装に直接対応するテスト
- 設定変更と、その変更に必要なドキュメント更新
- 同一機能を成立させる複数ファイルの変更
- ファイル移動と、それに伴う参照先の修正
- 依存関係の変更と、それに必要なコード修正

次の変更は原則として別コミットに分割する。

- 独立してrevertできる複数の機能変更
- 振る舞いの変更と無関係なリファクタリング
- 内容変更とリポジトリ全体のフォーマット変更
- 今回の依頼と、作業中に偶然発見した別問題の修正
- 独立した複数ツールやコンポーネントの変更
- 設定追加と、それに無関係なバージョン更新

リポジトリに `git/COMMIT_UNIT_GUIDE.md` が存在する場合は、その内容を優先する。

複数の目的を含む変更は、レビュー、revert、cherry-pickしやすい単位へ分割する。

`wip`、`fix typo`、`追加修正` などの後追いコミットを前提にせず、各コミット単体で意図を説明できる状態にする。

ただし、既存コミットの履歴整理はこのSkillでは行わない。

## 意図した変更だけをステージする

コミット対象のファイルを明示してステージする。

```bash
git add path/to/file
```

1つのファイルに複数の目的の変更が含まれる場合は、部分ステージを検討する。

```bash
git add -p
```

対話的な部分ステージを安全に実行できない環境では、無理にステージしない。

その場合は、次のいずれかを行う。

- 変更を安全に分離できるようファイルの差分を整理する
- コミットを行わず、分離できない理由をユーザーへ報告する

`git add .`、`git add -A`、`git commit -a` は原則として使用しない。

ただし、作業ツリー全体が今回の依頼だけで構成され、未追跡ファイルを含めてすべて確認済みであり、無関係な変更が存在しない場合に限り使用してよい。

コミット対象外の変更を勝手に戻したり、修正したり、削除したりしない。

## ステージ済み差分を確認する

コミット前に必ず次を実行する。

```bash
git diff --cached
git diff --cached --stat
git status --short
```

以下を確認する。

- ステージ済み差分が意図した変更だけで構成されている。
- コミットメッセージで説明できない変更が含まれていない。
- ファイル削除や移動が意図したものである。
- 秘密情報や不要なファイルが含まれていない。
- コミット対象外のユーザー変更が含まれていない。

問題がある場合はコミットせず、ステージ対象を修正する。

## コミットメッセージを作成する

リポジトリに `git/COMMIT_MESSAGE_GUIDE.md` が存在する場合は、その内容を優先する。

指定がない場合は、Conventional Commits形式を使用する。

```text
<type>[(<scope>)]: <description>
```

`scope` は必須ではない。

変更対象を明確に識別できる場合だけ使用し、適切なscopeが存在しない場合は省略する。

### type

変更内容に最も適したtypeを選択する。

- `feat`: 新しい機能や利用可能な振る舞いの追加
- `fix`: 不具合の修正
- `docs`: 文書だけの変更
- `refactor`: 外部動作を変えないコード構造の変更
- `test`: テストの追加や修正
- `build`: ビルドシステムや依存関係の変更
- `ci`: CI設定やCIスクリプトの変更
- `perf`: 性能改善
- `style`: 動作に影響しない書式変更
- `chore`: 上記に該当しない保守作業

`chore` を安易な受け皿として使用しない。

### scope

`scope` は、変更対象を識別できる最小の論理単位とする。

次の優先順位で選択する。

1. 独立したツール、パッケージ、サービス、コンポーネント名
2. リポジトリ内の主要ディレクトリまたはモジュール名
3. 複数箇所にまたがる変更に共通する機能領域
4. 適切な論理単位が存在しない場合はscopeを省略する

同一リポジトリ内では、既存コミットで使用されているscopeとの一貫性を考慮する。

次のような、変更対象を十分に説明しない抽象的なscopeは避ける。

- `config`
- `file`
- `misc`
- `update`
- `change`
- `other`

Dotfilesリポジトリでの例:

```text
feat(mise): ghの管理設定追加
docs(bootstrap): 新規環境への移行手順追加
fix(zellij): ロック切り替えキーバインドの修正
refactor(wezterm): 設定ファイル構成の整理
docs: リポジトリ概要の更新
```

### description

日本語のdescriptionは、簡潔な体言止めを基本とする。

変更したファイル名ではなく、変更の目的または結果を書く。

良い例:

```text
feat(mise): ghの管理設定追加
docs(bootstrap): 必須パッケージの導入手順追加
fix(zellij): ロック解除キーバインドの修正
refactor(git): コミット規約の責務分離
```

避ける例:

```text
chore: 修正
docs(readme): README更新
fix(config): 設定変更
chore(misc): いろいろ変更
```

破壊的変更がある場合は、リポジトリ規約に従って `!` または `BREAKING CHANGE` を使用する。

## コミットする

コミット直前に、ステージ済み差分とメッセージが一致していることを確認する。

```bash
git diff --cached
git commit -m "<type>[(<scope>)]: <description>"
```

コミットフックが失敗した場合は、原因を確認する。

今回の変更に起因する問題であり、安全に修正できる場合は修正して再検証する。

コミットフックを回避するために、明示的な依頼なしで次のオプションを使用しない。

```bash
git commit --no-verify
```

フック失敗を解決できない場合は、コミットせずユーザーへ報告する。

## コミット後に検証する

コミット後に次を実行する。

```bash
git status --short
git log --oneline --decorate -1
git show --stat --oneline --decorate HEAD
```

必要に応じて次も確認する。

```bash
git show --format=fuller --stat HEAD
git show --check HEAD
```

以下を確認する。

- 意図した変更がコミットされている。
- コミットメッセージが変更内容を正しく説明している。
- 意図しない変更がコミットされていない。
- コミット対象外の変更が勝手に消えていない。
- 未コミット差分が残っている場合、その内容と理由を把握している。

コミット後に未コミット差分が残っていても、それが既存のユーザー変更または明示的に対象外とした変更であれば、勝手に修正や削除を行わない。

## 完了報告

コミット後は、次を簡潔に報告する。

- 作成したコミットのハッシュ
- コミットメッセージ
- 実行した主要な検証
- 残っている未コミット差分の有無
- 検証できなかった項目がある場合はその内容

## 安全上の制約

- 共有済み履歴を書き換えない。
- 明示的な依頼なしにrebase、squash、fixup、commit amendを行わない。
- `git reset --hard` を使用しない。
- `git clean -fd` や `git clean -fdx` を使用しない。
- `git checkout -- .` や `git restore .` で作業ツリー全体を戻さない。
- 既存のユーザー変更を破棄、修正、削除、またはコミットへ混入させない。
- 秘密情報をコミットしない。
- コミットフックを明示的な依頼なしに回避しない。
- コミット対象を分離できない場合は、無理にコミットしない。
