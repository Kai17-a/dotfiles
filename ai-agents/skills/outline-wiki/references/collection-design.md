# コレクション設計と再編

コレクションの新設・分割・統合・大規模整理に使う。話題の分類より、情報を安全かつ継続的に管理できる境界を優先する。

## 判断順序

次の順で比較する。

1. 機密性と公開範囲
2. 閲覧者・編集者・管理者
3. 所有者・承認者
4. 更新・保存・廃止のライフサイクル
5. 話題・部署・製品

上位の条件が異なるほど別コレクションにする。話題だけが異なる場合は、原則として親子文書で整理する。

## 標準階層

次の構造を標準とする。

```text
コレクション
└── カテゴリ文書
    └── 個別文書
```

たとえば「勉強」コレクションでは、「Rust」をカテゴリ文書として置き、その配下に「ライフタイムについて」などの個別文書を置く。

- コレクション: 権限、所有者、ライフサイクルを共有する文書群
- カテゴリ文書: テーマ別の索引。カテゴリの目的、対象範囲、主要文書へのリンクを記載する
- 個別文書: 一つの知識、手順、議題を扱う本文

新規文書の配置時は、対象コレクションの文書ツリーを取得し、既存カテゴリを優先する。カテゴリ名の表記揺れや類義語を確認し、同じ意味のカテゴリを増やさない。サブカテゴリは文書量や発見性から必要な場合だけ作り、通常は3段構造より深くしない。

## 分割・統合を判定する

### 分割する

次のいずれかが継続的に異なる場合に分割を検討する。

- 閲覧者、編集者、管理者
- 機密区分、外部公開の可否
- 業務所有者、改訂承認者
- 棚卸し周期、保存期間、廃止・移管の単位

「同じ権限を一括設定して事故が起きないか」「同じ責任者が棚卸しできるか」を確認し、どちらかが No なら分割候補にする。

### 分割しない

部署名、製品名、話題、見た目、文書数の多さだけを理由に分割しない。読者・権限・責任者・ライフサイクルが同じなら、索引となる親文書を置いて整理する。

親文書には、対象読者、主要文書への導線、正本、更新責任者を記す。階層は原則3段以内にし、深い階層で検索性を補おうとしない。

### 統合する

目的、読者、実効権限、責任者、ライフサイクルが両立し、重複または利用者の往復が減る場合に統合する。名前や内容が似ているだけでは統合しない。

文書の正本は一つにし、別の導線からはリンクする。統合元は直ちに削除せず、統合先への案内を置き、確認期間を経てアーカイブする。削除が必要なら別途承認を得る。

## 棚卸しと提案

対象ごとに次を調べる。

- 名前、URL/ID、目的、対象読者
- 所有者、編集者、管理者、グループ
- 文書数、階層、主要トピック、重複候補
- 最終更新、更新頻度、棚卸し・保存要件
- 公開状態、ゲスト、外部共有、公開リンク
- 主要な内部リンク、埋め込み、添付
- 未閲覧、権限不足、所有者不明などの未確認事項

タイトル一覧だけで判断せず、代表文書と重複候補の本文を読む。各コレクションを「維持」「親子文書化」「統合」「分割」「アーカイブ候補」「要確認」に分類する。

最低限、次を提示する。

1. 判定表: `コレクション / 判定 / 理由 / 提案先または新構成 / 要確認事項`
2. 変更マップ: `移動元 / 移動対象 / 移動先 / 実施順 / 例外`
3. 完了報告: `実施内容 / 対象リンク / 検証結果 / 未実施・未確認事項`

権限、公開、リンクに影響する場合は、それぞれの変更前後の差分も示す。

## 変更を安全に実行する

### 常時確認する

- 対象ID、件数、移動元、移動先、親子関係、所有者を確定する。
- 承認後に対象・件数・内容・最終更新時刻が変わったら、再取得して再承認を得る。
- 反映後に配置、件数、親子関係、主要リンク、公開状態を再取得して検証する。

同一コレクション内の単件の並べ替えや親変更では、個別の棚卸し表やパイロットを必須としない。依頼範囲の最小差分だけを反映する。

### 権限境界を越える場合

- 移動元と移動先の管理者、メンバー、グループ、個別共有、ゲスト、公開設定を確認する。
- 変更前後に閲覧・編集・管理できる主体を比較し、権限拡大と縮退を示す。
- 実効権限を取得・検証できない、または意図しない差分がある場合は実行を止める。
- 最小権限を既定とし、個別ユーザーより管理されたグループへの付与を優先する。

### 一括操作する場合

1. 対象ID、移動元・先、親子関係、権限、公開状態、主要リンク、更新時刻を記録する。
2. 復旧方法を定め、可能ならエクスポートまたは復元可能な記録を確保する。
3. 代表的な少数文書でパイロットを実行する。
4. 配置、階層、件数、権限、公開状態、リンク、検索性を検証する。
5. 問題がなければ小分けのバッチで進め、バッチごとに検証する。

件数不一致、競合更新、リンク切れ、意図しない権限差分を検知したら停止する。URL、公開リンク、内部リンク、通知などの挙動は、利用するツールまたは現行仕様で確認し、未確認の挙動を断定しない。

### 外部公開する場合

- 新規文書は非公開を既定とする。
- 本文、添付、画像、リンク先に個人情報、認証情報、顧客情報、社外秘、内部URLがないか確認する。
- 公開対象、想定読者、期限、解除担当、子文書・添付への影響を示して明示承認を得る。
- 期限到来時に公開を解除し、匿名アクセスできないことを再確認する。自動期限を設定できなければ、手動フォロー項目として残す。

## 避けること

- 組織図をそのままコレクション構造にする。
- プロジェクトごとに無条件で新しいコレクションを作る。
- 広い権限のコレクションに機密文書を例外的に置く。
- 同じ内容を複数コレクションへ複製する。
- 下書き、承認済み、廃止済みの文書を区別せず混在させる。
- 所有者不在の共有コレクションを作る。
- 権限確認なしで文書を移動する。
